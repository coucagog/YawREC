enregistrement 10 s, pause/reprise, vérification MP4 via ffprobe) sur la machine actuelle.

## Installation de l'environnement

- `npm install` → OK. Fournit le CLI Tauri npm (`npx tauri`, 2.11.1), utilisé à la place de

- LLVM 23.1.4 via `winget install LLVM.LLVM` → `C:\Program Files\LLVM\bin`.
- FFmpeg « full-shared » gyan.dev → `C:\ffmpeg` (extraction avec le `tar.exe` de Windows,

  `npx tauri build --no-bundle` (pas besoin des installeurs pour le test), avec
  `LIBCLANG_PATH=C:\Program Files\LLVM\bin`.

## Problèmes rencontrés et résolutions

### 1. `LNK1104` / `LNK1114` sur `mozjpeg-sys` (dépendance de `nokhwa`)

- Symptôme : `lib.exe` n'arrive pas à ouvrir son fichier temporaire (`lnk{GUID}.tmp`) puis,
  plus tard, à remplacer `libmozjpeg62.a` (code d'erreur 5, accès refusé).
- La même commande `lib.exe` passe à la main → verrouillage par l'analyse temps réel Defender.
- Tentatives sans effet : TEMP dédié, `-j 4`, `-j 1`, TEMP dans `target/`.
- Résolution :
  1. Exclusion Defender ajoutée par l'utilisateur (PowerShell admin) :
     `Add-MpPreference -ExclusionPath '...\yawrec\src-tauri\target'`
  2. Suppression du dossier `target/release/build/mozjpeg-sys-*` (archive `.a` à moitié écrite
     par les essais précédents) → `mozjpeg-sys` compile en 15 s.
- À faire après les tests : `Remove-MpPreference -ExclusionPath '...\src-tauri\target'`.

### 2. Versions Tauri npm ↔ Rust désalignées

- `Cargo.lock` est ignoré par git (`yawrec/.gitignore`), donc cargo résout les dernières crates
  (tauri 2.12.5, plugins 2.4–2.8) alors que `package-lock.json` fige `@tauri-apps/api` 2.11 etc.
  Le CLI refuse : « Found version mismatched Tauri packages ».
- Résolution (uniquement dans `Cargo.lock`, aucun fichier suivi modifié) via
  `cargo update -p <crate> --precise <version>` :

| Crate | Version épinglée | Remarque |
|---|---|---|
| tauri | 2.11.6 | aligné sur `@tauri-apps/api` 2.11 |
| tauri-plugin-dialog | 2.7.3 | npm 2.7.1 |
| tauri-plugin-notification | 2.3.3 | npm 2.3.3 |
| tauri-plugin-global-shortcut | 2.3.2 | npm 2.3.1 |
| tauri-plugin-fs | 2.5.2 | les 2.6+ exigent tauri 2.12 |
| tauri-runtime | 2.11.3 | 2.12.x → 27 erreurs de compilation dans `tauri` |
| tauri-runtime-wry | 2.11.4 | fait redescendre wry 0.55.1 / tao 0.35.3 |
| tauri-macros / tauri-codegen / tauri-build | 2.6.3 | macros 2.7.4 → `Error::UnexpectedMenuKind` introuvable |
| tauri-utils | 2.10.2 | imposé par `tauri-plugin` 2.7.2, compatible `^2.9.3` |

- Piste durable (non appliquée) : versionner `Cargo.lock` pour une app, ou monter les paquets
  npm `@tauri-apps/*` en 2.12 pour suivre les crates.

### 3. FFmpeg 9.0.2 incompatible avec `ffmpeg-next` 8

- La release « courante » de gyan.dev est désormais FFmpeg 9.0.2 : `ffmpeg-next` 8.1.0 échoue
  (14 erreurs : `AV_CODEC_ID_V410` absent, champs `AVCodec::pix_fmts` etc. supprimés,
  nouvelles variantes de `AVFrameSideDataType`).
- Résolution : FFmpeg 8.1.2 full_build-shared depuis
  `github.com/GyanD/codexffmpeg/releases/tag/8.1.2` → `C:\ffmpeg`
  (la 9.0.2 est conservée dans `C:\ffmpeg-9.0.2`). DLL de `resources/ffmpeg-dlls/` remplacées
  par celles de la 8.1.2, `cargo clean -p ffmpeg-sys-next -p ffmpeg-next`, rebuild.
- Piste durable : documenter dans le README / `build.ps1` la version FFmpeg attendue (8.x).

### 4. `scripts/test_audio.ps1` ne se lance pas sous Windows PowerShell 5.1

- Le fichier est en UTF-8 **sans BOM** : PS 5.1 le lit en ANSI, les `✓`/`é` cassent le parsing
  (« Jeton inattendu… »).
- Contournement (fichier du dépôt non modifié) : exécution d'une copie ré-encodée UTF-8 **avec**
  BOM dans le scratchpad.
- Piste durable : ré-enregistrer `scripts/test_audio.ps1` (et `check_log.ps1`) en UTF-8 avec BOM.

### 5. Lancement de l'app depuis l'agent : WebView2 refusée

- Premier passage du script : bloqué > 5 min, aucun MP4. `Start-Process` lui-même ne rend pas
  la main depuis le shell de l'agent.
- Lancé directement (`timeout 8 ./yawrec.exe`), le backend démarre correctement :
  `Encodeur sélectionné : libx264 (logiciel)` (NVENC/QSV/AMF indisponibles sur cette machine),
  Ctrl+Shift+R / Ctrl+Shift+P enregistrés, tray actif, serveur WS sur `:9799`.
- Mais : `failed to create webview: WebView2 error: 0x800700AA (ressource en cours d'utilisation)`.
  Aucun `msedgewebview2` orphelin, pas de lockfile, `AppData\Local\app.yawrec.desktop\EBWebView`
  non modifié depuis le 21/10 → l'écriture y est vraisemblablement refusée par le sandbox du shell
  de l'agent (écritures limitées au projet).
- Remarque : en mode release, les logs vont sur stdout ; `%TEMP%\yawrec.log` n'est pas mis à jour
  par ce build (dernier contenu : 21/10), donc `scripts/check_log.ps1` n'est pas exploitable ici.
- Suite : relance du test hors sandbox.

### 6. Passage hors sandbox : 8/10 annoncé, mais en réalité aucun enregistrement

- `test_audio.ps1` rapporte 8/10 (échecs : durée 44,98 s au lieu de ~10 s, pas de second MP4).
- **Faux positif** : le MP4 « trouvé » (`YawREC-1792578952.mp4`, 22 Mo) date du 21/10. Le script
  prend le MP4 le plus récent du dossier sans vérifier qu'il a été créé pendant le test.
  → Piste : filtrer sur `LastWriteTime` > heure de début du test. Noter aussi que le format de nom
  a changé dans le code (`YawREC_<AAAA-MM-JJ_HH-MM-SS>.mp4`, cf. `state.rs::compute_output_path`).
- Relance manuelle avec logs capturés : les raccourcis globaux fonctionnent
  (`▶ start_recording (screen=0, webcam=false)`), mais :
  - `Encoder init : FFmpeg : Permission denied` → `Aucune frame capturée — pas de MP4 produit` ;
  - WebView2 toujours en échec `0x800700AA`, même hors sandbox ;
  - `%TEMP%\yawrec.log` n'est pas réécrit (ouverture échouée, logs repliés sur stderr).
- Vérifié sans trouver de cause : le shell écrit bien dans `Videos\YawREC` (ACL normales :
  SYSTEM, Administrateurs, hp en contrôle total) ; un `cmd.exe` enfant y écrit aussi ;
  Accès contrôlé aux dossiers = 0 ; Smart App Control = 0 ; seul antivirus : Defender ;
  aucun événement de blocage Defender (1123/1124/1127) ; aucun processus ne verrouille
  `yawrec.log` ni le profil WebView2 ; runtime WebView2 155.0.4283.62.
- Hypothèse : restriction propre aux processus lancés depuis l'environnement de l'agent.
  À trancher en lançant `yawrec.exe` directement depuis la session de l'utilisateur.

### 7. Lancement par l'utilisateur et vraie cause : l'emplacement de l'exe

- Double-clic utilisateur : SmartScreen (« Éditeur inconnu », normal pour un exe local non signé),
  puis la fenêtre « s'affiche une seconde et se ferme ». En fait l'app reste en tâche de fond :
  3 instances `yawrec.exe` (parent `explorer.exe`, 13:12, 13:13, 13:14) tournaient, la 1re tenant
  Ctrl+Shift+R/P et le port 9799. Toutes arrêtées.
- Toujours aucune écriture de `%TEMP%\yawrec.log` depuis ces instances.
- Test décisif : même exe + mêmes DLL copiés dans `C:\Users\hp\yawrec-copy\` → le log est écrit,
  la WebView2 se crée, le frontend envoie ses `set_*` (qualité, audio, écran…).
- Copie simple (sans hard link) **dans** `target\release` → échec à nouveau.
  → La restriction dépend de l'emplacement `...\YawREC\yawrec\src-tauri\target\release`, pas du binaire
  (ni du hard link créé par cargo). Cause système exacte non identifiée.
- Contournement : test E2E exécuté sur `C:\Users\hp\yawrec-copy\yawrec.exe`.
- Note : une seconde instance n'est pas refusée (pas de single-instance) ; elle démarre sans raccourcis
  ni serveur WS (« HotKey already registered », `os error 10048`). Piste : `tauri-plugin-single-instance`.
